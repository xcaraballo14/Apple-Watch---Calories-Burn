2. HEALTHKIT DATA TYPES — COMPLETE INVENTORY

BurnReward uses the following HealthKit types across the Apple Watch app (which records the workout) and the iPhone app (which reads the saved workouts back). This is the complete and exhaustive list — no data type is accessed without declaration.

Data Type HKType Identifier Permission Purpose Retention
Active Energy Burned HKQuantityType(.activeEnergyBurned) READ
Watch (live) · iPhone		 The Watch reads the live kilocalorie sum from HKLiveWorkoutBuilder during a quest, comparing it to the reward's calorie goal to fill the EXP bar and fire milestone haptics. The iPhone reads the calories stored on each saved BurnReward workout to build quest history, XP, and records. In-memory during the workout; the Watch keeps the current quest's value in UserDefaults until a new quest starts. The iPhone recomputes from HealthKit on every refresh and stores no copy.
Heart Rate HKQuantityType(.heartRate) READ
Watch (live) · iPhone		 The Watch shows live BPM and computes the workout average for the summary. The iPhone reads that average from each saved workout for the quest summary/receipt and the XP intensity factor. In-memory during the workout; the Watch keeps the summary average in UserDefaults until a new quest. The iPhone recomputes from HealthKit, no copy.
Step Count HKQuantityType(.stepCount) READ
Watch (live) · iPhone		 The Watch shows live steps during a quest. The iPhone reads the step total from each saved workout for the quest detail and the "most steps" personal record. In-memory during the workout; the iPhone recomputes from HealthKit on refresh, no copy.
Workout (HKWorkout) HKWorkoutType.workoutType() WRITE Watch
READ iPhone		 WRITE (Watch): when the quest's goals are met, the HKWorkoutSession is finalized and the HKWorkout is saved to Apple Health via finishWorkout(), stamped with the reward's name, emoji, and calorie goal as workout metadata, so it counts toward the user's rings. READ (iPhone): the app queries the workouts BurnReward itself saved (matched by app source) and reconstructs the entire quest history, level, badges, records, and weekly challenge from them — nothing is stored separately. Once written, the workout is owned and managed by Apple Health. BurnReward keeps no copy; the iPhone reads it fresh on each refresh.

HealthKit Privacy Note: Apple's HealthKit intentionally hides read-authorization status from apps (a privacy design so an app can't infer which categories a user has blocked). BurnReward therefore never drives its UI from HealthKit's read-status APIs — it relies only on real operations (a save succeeding, samples arriving). If a quest collects no sensor data, the Watch shows a one-time "no sensor data" hint pointing to iPhone Settings › Privacy & Security › Health › BurnReward. The iPhone reads only the workouts BurnReward itself saved (matched by app source) — never any other app's health data.

3. ON-DEVICE STORAGE — COMPLETE INVENTORY

BurnReward stores data exclusively on the user's own devices — never on a server. The Apple Watch uses UserDefaults (standard on-device key-value store) plus an App Group container shared with the watch-face complication; the iPhone uses its own on-device UserDefaults. Nothing here is transmitted off the device.

3C. iPHONE — USERDEFAULTS (STANDARD)

The iPhone app derives everything it shows from the workouts already saved in Apple Health, so it stores no health data of its own. Its UserDefaults holds only the profile fields the user chooses, the user's reward library, notification preferences, and small "already handled" markers so celebrations and prompts fire once.

KeyData StoredPurposeWhen Cleared
br.displayName String — the display name the user types on their profile (blank by default) Shown on the character sheet and Home header When the user clears it, or on app deletion
br.avatarJPEG Data — an optional profile photo the user picks, downscaled to a ~256 px JPEG Shown as the profile avatar. Stored locally and never uploaded When the user removes the photo, or on app deletion
br.rewardLibrary JSON — the user's custom reward definitions and built-in show/hide state The Reward Forge library; synced to the watch via WatchConnectivity On app deletion
br.ios.seenBadgeIDs Array of badge ID strings Records which badges were already celebrated so a toast fires only once On app deletion
br.ios.prBurn, br.ios.prDuration, br.ios.prSteps Integers Your current best burn / duration / steps, used to detect when a new personal record is set On app deletion
br.ios.notifiedLevel Integer The last level a notification was sent for, to avoid duplicate level-up alerts On app deletion
br.ios.alertsLastSeen Timestamp When the alerts bell was last opened — drives the unread dot On app deletion
br.ios.didRequestHealthAuth Boolean One-shot flag so the Health permission sheet is shown at most once On app deletion
br.notifyAchievements, br.notifyStreak, br.notifyChallenge, br.notifyStreakMinutes Booleans + an integer (minutes) Notification preferences — which reminders are on, and the reminder time On app deletion

Local notifications: The iPhone schedules badge, level-up, record, streak, and weekly-challenge reminders with UNUserNotificationCenter. They are composed and delivered entirely on-device — there is no push server, no device token, and nothing is transmitted.

Key point: The only user-provided data is an optional display name and profile photo, both stored on the device and never transmitted. Everything else is numeric workout metrics, reward names from the user's own list, timing data, and app preferences. There are no accounts, no email addresses, no device-identifier tracking, and none of it leaves the device.

5. APPLE APP STORE COMPLIANCE

APP STORE CONNECT — DATA NUTRITION LABEL

Apple's "App Privacy" questionnaire defines collection as transmitting data off the device for access beyond servicing the immediate request. BurnReward reads HealthKit entirely on-device, stores everything locally, runs no server, and bundles no analytics or third-party SDKs — so nothing meets that definition. The accurate response is Data Not Collected.

CategoryCollected?Linked to Identity?Used for Tracking?
Contact Info✗ Not collected——
Health & Fitness✗ Not collected (read on-device only, never transmitted)——
Financial Info✗ Not collected——
Location✗ Not collected——
Sensitive Info✗ Not collected——
Identifiers✗ Not collected——
Usage Data✗ Not collected——
Diagnostics✗ Not collected——

Result: Data Not Collected. Health data (active energy, heart rate, workouts) is read from HealthKit and used only on the device to update the user's quest — never transmitted, stored off-device, sold, or shared. Because it never leaves the device, it is not "collected" under Apple's App Privacy definition, so BurnReward's store privacy label is Data Not Collected.

This concerns on-device collection for the App Store label only. HealthKit data is still processed on-device to power the app; the broader frameworks that also cover on-device processing (GDPR, CCPA) are addressed in Section 6.

6. REGULATORY COMPLIANCE

GDPR (EU General Data Protection Regulation)

Lawful basis for processing ✓ Consent via HealthKit permission dialog (Article 6(1)(a)) and legitimate interest in app functionality (Article 6(1)(f))

COPPA (Children's Online Privacy Protection Act)

BurnReward is not directed to children under 13. The App Store age rating is set to 4+ (no objectionable content), but the app is a fitness tool intended for adults and teens with parental consent. No personal information is collected from any user, so COPPA obligations regarding data collection and parental consent for personal information do not apply. The Terms of Service set a minimum age of 13.

HIPAA (Health Insurance Portability and Accountability Act)

HIPAA applies to covered entities (healthcare providers, insurers) and their business associates. BurnReward is a consumer fitness app, not a healthcare provider, and does not create, receive, maintain, or transmit Protected Health Information (PHI) as defined by HIPAA. The app does not interface with any healthcare provider system and is not a medical device. HIPAA does not apply.
