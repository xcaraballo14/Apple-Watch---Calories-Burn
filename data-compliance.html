2. HEALTHKIT DATA TYPES — COMPLETE INVENTORY

BurnReward requests the following HealthKit permissions. This is the complete and exhaustive list — no data type is accessed without declaration.

Data Type HKType Identifier Permission Purpose Retention
Active Energy Burned HKQuantityType(.activeEnergyBurned) READ Core metric. The live kilocalorie sum from the HKLiveWorkoutBuilder is read every time the sensor pushes new data. It is compared against the user's selected calorie goal to update the EXP progress bar and trigger reward milestones at cumulative thresholds. In-memory during workout. Final value persisted on-device via UserDefaults (br.caloriesBurned) until the user starts a new quest. Cleared by tapping "NEW QUEST."
Heart Rate HKQuantityType(.heartRate) READ The most-recent BPM value is displayed live on the workout screen. The running average from the builder is used to populate the AVG ♥ field in the workout summary. In-memory during workout. Summary average persisted on-device via UserDefaults (br.summaryAvgHR) until a new quest starts.
Workout (HKWorkout) HKWorkoutType.workoutType() READ WRITE READ: Used solely to check authorization status (HealthKit hides read-permission state, so workout share-status is used as a proxy to detect if the user has denied access). WRITE: When the user completes all quest goals, the HKWorkoutSession is ended and the HKWorkout record is finalized and saved to Apple Health via HKLiveWorkoutBuilder.finishWorkout(). This makes the session count toward the user's rings and workout history. Once written to HealthKit, the workout record is owned and managed by Apple Health. BurnReward retains no copy and has no further access to it.

HealthKit Privacy Note: Apple's HealthKit framework intentionally does not disclose read-authorization status to apps (it always returns .notDetermined for read types). This is an Apple privacy design decision to prevent apps from inferring which health categories a user has blocked. BurnReward uses the workout share authorization status as a proxy only to determine whether to show the "Health Access Needed" error screen.

3. ON-DEVICE STORAGE — COMPLETE INVENTORY

BurnReward stores data exclusively on the user's Apple Watch using two mechanisms: UserDefaults (standard on-device key-value store) and an App Group container shared between the app and the watch-face complication extension.

3A. USERDEFAULTS (STANDARD)

KeyData StoredPurposeWhen Cleared
br.activeRewardIDs Array of reward name strings (e.g., ["Taco", "Donut"]) Restores the active quest rewards if the app is relaunched mid-workout On new quest start or app deletion
br.phase String: "workout" or "earned" Restores the correct screen (workout view vs. earned screen) on relaunch On new quest start
br.earnedCount Integer (0–2) Tracks how many combo rewards have been earned in the current quest On new quest start
br.caloriesBurned Double (kilocalories) Restores live progress on relaunch; final value shown in summary On new quest start
br.startDate TimeInterval (seconds since reference date) Allows the elapsed-time counter to continue correctly after relaunch On new quest start
br.summaryDuration Integer (seconds) Workout duration shown on the earned screen; survives app relaunch On new quest start
br.summaryAvgHR Integer (BPM) Average heart rate shown on the earned screen; survives relaunch On new quest start
br.summaryCalories Integer (kilocalories) Total calories shown on the earned screen; survives relaunch On new quest start

3B. APP GROUP CONTAINER (COMPLICATION SHARING)

App Group ID: group.com.burnreward.app

KeyData StoredPurposeWhen Cleared
br.snapshot JSON-encoded BurnRewardSnapshot: { isActive: Bool, emoji: String, caloriesBurned: Int, totalGoal: Int } Passed to the WidgetKit complication extension so the watch face can display live quest progress (emoji + calorie arc). Updated on every state change. Reset to inactive state on new quest start or app deletion

Key point: None of the above data contains personally identifiable information (PII). The stored values are numeric workout metrics, selected food names from a fixed list, and timing data — there are no names, email addresses, device identifiers, or biometric fingerprints stored by BurnReward.

4. DATA FLOWS — ARCHITECTURE DIAGRAM

All data flows are local. There is no outbound network path from BurnReward to any server.

SourceFlowDestinationNetwork?
Apple Watch sensors (HR, accelerometer) → HealthKit → HKLiveWorkoutBuilder → WorkoutManager (in-app) In-app UI (EXP bar, live stats) ✗ No

WorkoutManager (in-app) → App Group UserDefaults Complication extension (same device) ✗ No

COPPA (Children's Online Privacy Protection Act)

BurnReward is not directed to children under 13. The App Store age rating is set to 4+ (no objectionable content), but the app is a fitness tool intended for adults and teens with parental consent. No personal information is collected from any user, so COPPA obligations regarding data collection and parental consent for personal information do not apply. The Terms of Service set a minimum age of 13.

HIPAA (Health Insurance Portability and Accountability Act)

HIPAA applies to covered entities (healthcare providers, insurers) and their business associates. BurnReward is a consumer fitness app, not a healthcare provider, and does not create, receive, maintain, or transmit Protected Health Information (PHI) as defined by HIPAA. The app does not interface with any healthcare provider system and is not a medical device. HIPAA does not apply.
